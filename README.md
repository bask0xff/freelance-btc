# Freelance BTC — MVP

Фриланс-биржа с оплатой только в Bitcoin. Эскроу-модель: **1 заказ = 1 уникальный депозитный адрес**,
средства до релиза лежат в общем хот-кошельке вашей bitcoind-ноды (кастодиальная модель),
привязка "какая сумма чья" ведётся в **PostgreSQL**.

## Architecture

```
Клиент → создаёт заказ (status: open) → фрилансеры видят его в GET /api/orders/open

Фрилансер → POST /orders/:id/apply (можно предложить свою цену) → отклик status: pending

Клиент → GET /orders/:id/applications → смотрит отклики →
    POST /orders/:id/hire {application_id} →
        - freelancer_id проставляется в заказ, amount_btc обновляется, если фрилансер предложил свою цену
        - остальные pending-отклики автоматически отклоняются
        - backend вызывает getnewaddress(label="order_N", "bech32")
        - заказ переходит в awaiting_payment, адрес показывается клиенту

Фоновый Scanner (раз в 60 сек, как ваш while True + sleep) →
    listtransactions("*", 1000) → ищет receive-транзакции на адреса заказов →
    пишет в btc_transactions → при confirmations >= BTC_MIN_CONFIRMATIONS
    переводит заказ в funded

Клиент подтверждает сдачу работы → заказ delivered →
    POST /api/orders/:id/release → walletpassphrase (разблокировка на 30 сек) →
    sendtoaddress(payout_address_фрилансера) → walletlock → заказ completed
```

## Components

- `backend/` — Go (Gin) API + фоновый сканер транзакций + обёртка над bitcoind JSON-RPC
  (`internal/bitcoin/client.go` — прямой аналог вашего `AuthServiceProxy`, тем же набором вызовов:
  `getnewaddress`, `listtransactions`, `walletpassphrase`, `sendtoaddress`, `getbalance`).
- `backend/internal/db/migrations/` — версионированные SQL-миграции (`golang-migrate`), применяются
  автоматически при старте backend'а (см. ниже).
- `frontend/` — Vue3 + TypeScript + Vite, простая форма создания заказа и получения адреса оплаты.
- `docker-compose.yml` — postgres + backend + frontend. **bitcoind не контейнеризован** — он у вас уже
  работает на хосте, backend достучится до него через `host.docker.internal`.

## Build & Launch

```bash
cp .env.example .env
# заполните BTC_RPC_USER / BTC_RPC_PASSWORD / BTC_WALLET_PASSPHRASE вашими реальными значениями
# (теми же, что в btc_check.py)

docker compose up --build
```

Миграции применяются автоматически при старте контейнера `backend` — отдельно накатывать
`CREATE TABLE` не нужно, это не MySQL-скрипт в `docker-entrypoint-initdb.d`, а полноценный
инструмент версионирования схемы (`golang-migrate`), встроенный в бинарник через `go:embed`.

- Frontend: http://localhost:5180
- Backend health-check: http://localhost:8099/health
- PostgreSQL (если нужно подключиться снаружи, например DBeaver/psql): `localhost:5436`

Порты подобраны так, чтобы не конфликтовать с вашими текущими контейнерами (8080/8081/8082/8085/8088,
5432/5433/5435, 5672/5673, 6379/6380, 15672/15673, 3002 — все заняты другими проектами). Если у вас
появятся новые сервисы и снова возникнет конфликт — поменяйте маппинг портов слева от `:` в
`docker-compose.yml` (`"5436:5432"`, `"8099:8080"`, `"5180:5173"`), правая часть (порт внутри
контейнера) трогать не нужно.

> **Важно:** в вашем `bitcoin.conf` должно быть разрешено подключение с IP докер-моста, а не только
> 127.0.0.1 — иначе RPC не пустит контейнер. Добавьте `rpcallowip=172.16.0.0/12` (диапазон докер-сетей)
> и `rpcbind=0.0.0.0:8332` (или конкретный интерфейс), либо явно пропишите bridge IP. Порт 8332 у вас
> сейчас не занят другими контейнерами (bitcoind, судя по всему, работает нативно на хосте, не в докере).

## Migrations

Файлы лежат в `backend/internal/db/migrations/`, формат имён — конвенция `golang-migrate`:
`<версия>_<название>.up.sql` / `.down.sql`. При старте backend вызывает `db.RunMigrations()`
(`internal/db/migrate.go`), который накатывает все ещё не применённые версии — прогресс отслеживается
в служебной таблице `schema_migrations`, которую PostgreSQL создаёт сам.

**Добавить новую миграцию:** создайте `000003_your_change.up.sql` и `.down.sql` рядом с существующими —
номер по порядку, откат обязателен (даже если "просто дропнуть таблицу").

**Откатить миграцию вручную** (нужен CLI, `go install github.com/golang-migrate/migrate/v4/cmd/migrate@latest`):
```bash
export DATABASE_URL="postgres://postgres:<пароль>@localhost:5436/freelance_btc?sslmode=disable"
make migrate-down   # откатит одну последнюю миграцию
```

## Тесты

Юнит-тесты бэкенда используют `sqlmock` (мок `*sql.DB`, реальная БД не нужна) и httptest-заглушку
bitcoind там, где сервис реально стучится по RPC (найм фрилансера генерирует адрес).

```bash
make test           # go test ./...
make test-verbose   # с подробным выводом по каждому кейсу
```

Покрыто: JWT (генерация/валидация/протухание/чужой secret), сканер транзакций (чистая функция
определения статуса по числу подтверждений), регистрация/логин (валидация email/пароля, дубликат
email как реальная ошибка Postgres 23505, неверный пароль), создание заказа и наём фрилансера
(включая happy path через транзакцию и два сценария отказа), отклики (не найден/не открыт/успех/с
предложенной ценой, отзыв отклика).

Внешние вызовы (реальный bitcoind, реальный Postgres) в тестах не участвуют — это осознанно юнит-,
а не интеграционные тесты. Для интеграционных потребуется testcontainers-go с реальным Postgres —
если понадобится, скажите, добавлю отдельным слоем.

## Отклики и наём (v0.4)

- `GET /api/orders/open` — открытые заказы для фрилансеров
- `POST /api/orders/:id/apply` (роль freelancer) — отклик, опционально со своей ценой
- `GET /api/orders/:id/applications` — список откликов, доступен только клиенту-владельцу заказа
- `DELETE /api/applications/:id` (роль freelancer) — отозвать свой отклик
- `POST /api/orders/:id/hire` (роль client) — нанять по конкретному отклику: только теперь
  генерируется депозитный адрес и заказ переходит в `awaiting_payment`
- `POST /api/orders` теперь требует роль `client` (раньше — любой авторизованный пользователь)

## Что уже готово (v0.5 — Postgres + миграции + тесты)

- **PostgreSQL** вместо MySQL: драйвер `jackc/pgx/v5`, все запросы переведены на `$1..` плейсхолдеры,
  `RETURNING id` вместо `LastInsertId()`, `ON CONFLICT` вместо `ON DUPLICATE KEY UPDATE`
- **Версионированные миграции** (`golang-migrate`), применяются автоматически при старте
- **Тесты** для auth/bitcoin/user/order/application (см. раздел выше)
- **Авторизация**: регистрация (`POST /api/auth/register`), логин (`POST /api/auth/login`), JWT-токены
  (HS256, срок жизни настраивается `JWT_TTL_MINUTES`), middleware защиты роутов, роли `client`/`freelancer`
- Пароли хранятся как bcrypt-хэш, email валидируется
- `GET /api/me` — профиль текущего пользователя, `PUT /api/me/payout-address` — фрилансер указывает
  свой BTC-адрес для выплат
- Отклики и наём (см. выше)
- Фоновый сканер входящих платежей (аналог вашего цикла listtransactions)
- Ручной release эскроу через API (`POST /api/orders/:id/release`)
- Frontend: формы логина/регистрации, форма создания заказа, сохранение payout-адреса; токен хранится
  в `localStorage` (это обычный SPA, не artifact-песочница claude.ai, так что localStorage тут уместен)

## Чего пока нет — следующие шаги

1. **UI для откликов/найма** — backend готов, но фронтенд пока не обновлён под этот флоу (нет экрана
   "открытые заказы" для фрилансеров, формы отклика, списка откликов у клиента)
2. **Переход in_progress → delivered** — пока нет эндпоинта, которым фрилансер сообщает о сдаче работы
3. **Логика диспутов** — сейчас только таблица в БД, нет API/UI для открытия и разрешения спора
4. **Уведомления** о поступлении платежа (WebSocket/SSE вместо ручного обновления страницы)
5. **Безопасность приватного ключа кошелька**: сейчас `BTC_WALLET_PASSPHRASE` лежит в `.env` рядом с
   backend — на проде вынести в секрет-хранилище (Vault/Docker secrets), не в plain env
6. **Комиссия платформы** — сейчас релиз отправляет 100% суммы фрилансеру, нужно вычитать fee
7. **Учёт комиссии майнеров (network fee)** при sendtoaddress — сейчас берётся дефолтная политика кошелька,
   стоит сделать управляемой (subtractfeefromamount и т.д.)
8. **Refresh-токены** — сейчас только access-токен на 7 дней, нет revoke/refresh механизма
9. Опционально в будущем — переход части сделок (крупные заказы) на 2-из-3 мультисиг вместо
   чисто кастодиальной модели
10. **Интеграционные тесты** с реальным Postgres (testcontainers-go) — сейчас только юнит-тесты с моками

## Безопасность / регуляторика (важно проговорить отдельно)

Кастодиальная модель эскроу означает, что платформа физически может распоряжаться средствами клиентов.
Это накладывает как минимум:
- Нужен явный ToS с описанием условий удержания и релиза средств
- Желательно логировать/аудировать каждый sendtoaddress
- В зависимости от юрисдикции может требоваться регистрация как VASP (Virtual Asset Service Provider)

Это не блокирует разработку MVP, но стоит иметь в виду при выходе в продакшн.
